# 架构技术路线升级版（2026）

版本：v1.0  
日期：2026-05-20  
目标：从“功能拼接态”升级到“产品运营态 + 自我进化态”。

---

## 1. 现状架构（As-Is）

## 1.1 当前结构

- 前端：React + Vite + TS
- 后端：FastAPI（/api/v1 与 /api 双体系）
- 网关：LiteLLM
- 向量：Qdrant
- 能力：Team/Project/Agent/Knowledge + Governance + Observe

## 1.2 主要问题

- 用户路径不连续（权限链路强但引导弱）
- 知识入口不完整（上传缺失）
- 编排与治理能力未产品化
- 观测缺少统一事件与追踪闭环
- 架构职责边界文档化不足

---

## 2. 目标架构（To-Be）

## 2.1 四层架构

1. Experience Layer（产品层）
- 统一工作台：项目、知识、流程、治理、观测
- 角色化入口：管理员/运营/研发

2. Control Plane（控制面）
- Workflow Service（编排）
- Capability Registry（Skill/RAG/Agent/MCP 注册）
- Policy & Evolution Service（策略与进化）
- Release Service（发布、灰度、回滚）

3. Gateway & Runtime（网关执行层）
- LiteLLM（模型路由、预算、日志、MCP/A2A）
- Tool Runtime（调用执行、超时、重试）

4. Data & Observability（数据观测层）
- Postgres（元数据）
- Qdrant（向量）
- 统一事件总线 + Trace（request_id / call_id）

---

## 3. 关键升级点

## 3.1 API 体系收敛

- 收敛 /api/v1 与 /api 的语义边界
- 对外统一“业务任务 API”
- 保留底层能力 API 作为内部接口

## 3.2 能力对象化

统一对象：
- Capability
- Version
- Binding
- Policy
- Runtime Contract

结果：Skill/RAG/Agent/MCP 不再是碎片接口，而是可治理资产。

## 3.3 发布治理体系

- 草稿 -> 校验 -> 灰度 -> 全量 -> 回滚
- 发布单必须包含：变更说明、影响范围、回滚点
- 所有发布可审计

## 3.4 观测统一化

- 前端事件、后端日志、LiteLLM call_id 统一关联
- 统一指标：成功率、P95、成本、回滚次数、质量分
- 增加“变更影响分析”看板

---

## 4. 分阶段路线图

## P0（0-2周）：可用性修复

- 新手引导和默认路径
- 知识上传入口 V1
- 用户管理入口收敛
- 错误提示产品化

成功标志：用户能独立完成首个业务闭环。

## P1（2-6周）：控制面基础成型

- Workflow 编排 V1（模板化）
- Capability Registry V1
- 发布/回滚 V1
- 统一事件模型 V1

成功标志：能力可版本化发布和回滚。

## P2（6-12周）：自我进化能力上线

- 策略评估与候选生成
- 自动灰度与效果比较
- 成本-质量联合优化

成功标志：平台具备持续优化闭环，不依赖人工频繁调参。

## P3（12周+）：组织级治理

- 多租户组织治理模型
- 预算策略自动化
- 运营报表和审计标准化

成功标志：可规模化服务多个团队并稳定运营。

---

## 5. 组织与运维治理升级

## 5.1 角色分工

- Product Owner：定义业务流程与验收
- Platform Engineer：控制面与网关集成
- AI Engineer：策略、评估、质量优化
- SRE：稳定性、容量、告警、应急

## 5.2 运维机制

- 变更窗口 + 灰度机制
- 事故分级与复盘模板
- SLO：可用性、延迟、错误率、成本偏差

---

## 6. 风险与缓解

风险：
- 历史接口兼容性
- 功能并行开发导致架构漂移
- 观测改造引发性能损耗

缓解：
- 双轨兼容与弃用计划
- 架构评审门禁（每迭代）
- 指标采样和日志分层存储

---

## 7. 北极星指标

- 首次可用时间（TTFV）<= 30 分钟
- 变更可回滚率 = 100%
- 故障定位平均时长下降 >= 60%
- 业务请求可追踪覆盖率 >= 90%
- 成本偏差（预测 vs 实际）<= 10%

---

## 8. 最终路线判断

升级方向不是“继续叠功能”，而是“建立控制面中台能力”。  
即：以 LiteLLM 做稳定网关，以自建控制面承接产品与进化能力，形成长期可维护技术路线。
