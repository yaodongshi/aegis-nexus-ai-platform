# 开源 Harness 平台评估与选型建议（2026-06-02）

## 结论先行

- 目前不存在一个可直接无缝替代你们现有控制面与治理面的“全栈开源 Harness 平台”。
- 开源方案可以显著补强你们的执行编排与多智能体运行时，但不能直接替代你们的平台业务模型、网关治理和组织流程。
- 你们方案不会没用，正确路线是“保留自有控制面 + 引入开源 Harness 运行时”。

## 已核查的主流开源方向

## 1) LangGraph

定位：长周期、有状态、可中断、可人工介入的编排底座。  
强项：持久化执行、状态图、人机协同、内存与可观测体系成熟。  
短板：不是开箱即用的企业控制面，需要二次封装。  
适配度：高，适合作为你们 Agent Harness 的执行内核。

## 2) OpenHands

定位：偏软件工程自动化智能体平台（CLI/GUI/SDK/Cloud）。  
强项：开发任务执行链路完整，工程社区活跃，落地快。  
短板：企业控制面与治理能力存在商业版边界，深度定制成本不低。  
适配度：中高，适合参考其执行器与沙箱设计，不建议直接整体替换。

## 3) CrewAI

定位：多智能体编排框架（Crew + Flow）。  
强项：流程表达简单，事件驱动能力较强。  
短板：企业级控制面更多在商业组件，开源版仍需自建治理层。  
适配度：中，适合做业务流程编排补充。

## 4) OpenAI Agents SDK（Python）

定位：轻量多智能体开发框架，含工具、护栏、会话、追踪、Sandbox Agent。  
强项：接口清晰、运行时能力现代。  
短板：仍是 SDK 级，不是完整组织级控制面。  
适配度：高，适合作为执行层引擎之一。

## 5) AutoGen（现状）

现状：官方仓库已维护模式，官方建议迁移到 Microsoft Agent Framework。  
结论：不建议作为你们新主路线。

## 你们与开源 Harness 的关系（关键判断）

你们当前已有：
- 控制面对象与治理接口（sessions、policies、approvals、v2 key policy）
- 网关模型同步、配置落地与回滚审计
- 演进动作日志、模板回放与工作流生成/优化入口

你们当前缺失：
- 强约束执行状态机（物理锁）
- 角色解耦运行时（planner/executor/evaluator）
- 自动灰度比较与策略晋级/降级
- 统一轨迹追踪标准（跨前后端与网关）

结论：你们更像“控制面中台 + 演进原型”，最优做法是挂接开源运行时，而不是推倒重来。

## 面向团队自动进化 + API 虚拟化的落地路线

## 阶段 A：保留现有控制面，补 Harness 运行时（2-4 周）

- 选 LangGraph 或 OpenAI Agents SDK 作为执行编排内核。
- 你们后端保留为唯一真理源：Policy、Approval、Key、Workflow、Action Log。
- 每次执行前强制唤醒协议：环境状态、代码状态、任务状态三步校验。

## 阶段 B：引入“物理锁”与可验证完成标准（2-4 周）

- 增加 Task Plan Lock（JSON 状态机）。
- 只允许工具更新状态，不允许模型自由宣布完成。
- 失败自动回滚到最近可验证状态，并记录可重放轨迹。

## 阶段 C：自动进化闭环（4-8 周）

- 以成功率、延迟、成本、回滚率作为目标函数。
- 小流量自动灰度比较策略 A/B。
- 胜出策略自动晋级，失败策略自动降级并沉淀经验模板。

## API 虚拟化建议（你们语境）

目标：让业务调用看到稳定契约，不被底层模型和工具波动影响。

建议：
- 建立 Virtual Capability API（能力别名层），例如 chat-default、embed-default。
- 将 provider 差异、模型版本、参数兼容收敛在网关与控制面，不暴露给业务方。
- 对外提供版本化能力合同（输入/输出 schema + SLA + 预算策略）。
- 把审批、限流、熔断、回滚挂在能力别名上，而不是挂在具体模型上。

## 是否可以直接使用完整开源方案

可以直接用的部分：
- 执行编排引擎
- 多智能体运行时
- 工具调用与部分观测能力

不能直接替代的部分：
- 你们的组织治理逻辑
- 你们的业务对象模型（Team/Project/Key/Policy/Approval）
- 你们的网关策略与发布回滚流程

最终建议：
- 不建议全量替换。
- 建议“开源运行时 + 自有控制面”双层架构。
- 你们现有方案不是包袱，而是未来护城河核心。
